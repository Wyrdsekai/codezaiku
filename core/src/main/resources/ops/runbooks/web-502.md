# Runbook: a web endpoint returns 5xx / connection refused (502 Bad Gateway)

A 502 means the front proxy (nginx) is UP but its UPSTREAM did not answer. The 502 is the LAST link in a
chain — never the root cause. Trace the chain from the edge INWARD, and at each hop that is down, find why.

## The chain to walk
1. **Edge (proxy).** Confirm nginx is running and reproduce the 502: `nginx -t`, `ss -ltnp | grep :80`,
   `curl -si localhost`. Read nginx's error log: `tail -50 /var/log/nginx/error.log` — a 502 logs the
   upstream it tried and why (`connect() failed (111: Connection refused) while connecting to upstream`).
   That names the next hop (host:port).
2. **Upstream app.** Is it listening? `ss -ltnp | grep :<upstream_port>`. If NOT, the app is down — that is
   hop 2, still a SYMPTOM. **Do not stop here; do not just "restart the app" — if something made it exit it
   will exit again.**
3. **Why did the app exit?** Read the APP's OWN log (its logfile under /var/log, or `journalctl -u <unit>`).
   Find the last FATAL line before it stopped. Common roots it will name:
   - a dependency it needs is unreachable (DB/cache/socket) → check THAT (its port, its own health) →
     which may itself be down for a reason (recurse).
   - it could not write (disk full / permission) → `df -h` the path it names.
   - bad config / missing file / bad env → the error names the file.
4. **Recurse until the log names a CONCRETE resource/config fault, not another "X is down".** The root is
   the deepest thing that failed on its own — e.g. `disk_full`, `bad_config`, an external dependency down.

## Conclude
State the ROOT (e.g. disk_full) AND the causal chain (disk full → app couldn't start → nginx 502), with the
exact log lines for each hop. A remediation that only touches the edge or restarts the app will not hold.
